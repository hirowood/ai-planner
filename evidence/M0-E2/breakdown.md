## 解釈

- **時間の 99% 以上が外部 API にある。** 自分のコードを速くしても体感は変わらない (grill T3 / E2 が実測で成立)。
- したがって直す対象は「外部 API の呼び方」になる。候補:
  - **chat**: 非ストリーミング (`chat.sendMessage` が全文を待つ) — 本人は毎回 3〜9 秒、何も表示されずに待っている。ストリーミングにすれば最初の文字が出るまでの時間は縮むが、全体の時間は変わらない。指標も「最初の文字まで」に変わる (今の 5 項目では測れない)。
  - **calendar/create**: イベントを `for` + `await` で 1 件ずつ順に登録している (`app/api/calendar/create/route.ts` の登録ループ)。並列にすれば、N 件の登録時間は [仮説] 最も遅い 1 件分近くまで縮む。今の `total_ms` / `calendar_ms` でそのまま測れる。
  - プロンプト長の削減 / モデル変更は PRD の Out of Scope (モデル選定) に近いので 1 周目では扱わない。

## 決定 (T-005 ゲート判定・2026-09-29)

- **[決定] 最初のカード = `api/chat` のストリーミング化**。本人の選択 (推奨 A)。
- 根拠の数字:
  - chat は total 中央値 8,283.9ms のうち gemini が 8,250.5ms (99.6%)。本人は 1 回の送信ごとに 3.3〜9.4 秒、何も表示されないまま待っている。
  - chat は 1 回の利用で約 5 回使われる (今回 n=5)。予定登録 (n=1) より、本番の判定に足りる件数が集まりやすい。
- 仮説の方向: **呼び方** (全文を待つ → 生成された分から送る)。全体の時間は変わらない前提で、「最初の文字が画面に出るまで」を縮める。モデル・プロンプトは変えない (PRD の範囲内)。
- **指標の追加**: 今の 5 項目では「最初の文字まで」を測れないので、`[perf]` に所要時間の項目を 1 つ足す ([仮] `first_chunk_ms`)。時間の値だけなので、本文を出さない制約は保たれる。PRD US1 の「5 項目」からの変更として、M2 の事前登録 (T-020) で定義と閾値を固定する。
- 2 枚目の候補: `api/calendar/create` の並列化 (今の指標で測れる)。

## n について

n は小さい (chat 5 / get 2 / create 1)。これは「どこに時間があるか」の偏りを見るには足りるが、改善の判定には使わない。
判定は M1 の実験室ベンチのばらつき (T-013) を基準にする。
